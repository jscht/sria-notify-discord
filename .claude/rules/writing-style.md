# 글쓰기 규칙 (Writing Style)

## 적용 대상
사람이 읽는 모든 글: 사용자에게 하는 답변·보고, README·docs/·.claude/ 문서, 코드 주석, 커밋·PR·리뷰 코멘트.

- 기본은 **간결하게** 쓴다. 아래 "단어 구분"과 "문장 쓰기"를 지킨다.
- 사용자가 **상세한 설명을 요청하면** 그때만 배경·이유·비교를 넣어 이해하기 쉽게 풀어서 설명한다.
  이 경우에도 ③(애매한 말)은 쓰지 않는다.
- 풀어서 설명한 내용을 문서·주석에 옮길 때는 요지만 남긴다.

## 단어 구분 — 세 가지

| 구분 | 무엇 | 처리 | 예 |
|------|------|------|----|
| ① 고유 이름 | 제품·서비스·명령어·파일·변수 이름 (검색하면 공식 문서가 나오는 것) | 그대로 쓴다. 코드·명령·파일·변수는 백틱으로 감싼다. 처음 나올 때 하는 일을 짧게 덧붙인다 | Secret Manager(비밀값 보관 서비스), `firebase functions:secrets:set`, `.env`, `REDIS_URL` |
| ② 업계 일반 용어 | 개발자라면 보통 아는 정식 용어 | 그대로 쓴다 | 배포, 환경변수, 캐시, 토큰, 암호화 |
| ③ 애매한 말 | 영어를 대충 옮긴 말, 동사로 쓴 업계 은어, 팀·세션 안에서만 통하는 줄임말과 코드명 | **쓰지 않는다.** 평범한 말로 풀어 쓴다 | 아래 표 |

### ③ 판별 기준
아래 중 하나라도 해당하면 ③으로 보고 풀어 쓴다.
1. 그 단어만 따로 떼어 검색하면 무슨 뜻인지 하나로 정해지지 않는다 (예: "시크릿", "주입")
2. 영어 단어를 우리말 동사처럼 쓴다 (예: "바인딩한다", "마운트된다")
3. 이 프로젝트 문서나 대화를 읽어야 뜻을 안다 (예: `O-4`, `E안`, `(C)/(U)`, "매치율")
4. "무엇을, 어디에"가 빠져 있어 앞 문맥이 없으면 대상을 알 수 없다 (예: "위 두 시크릿")

### ③ 바꿔 쓰기 예

| ❌ 애매한 표현 | ✅ 바꿔 쓴 표현 |
|---|---|
| 시크릿 | 비밀값(토큰·비밀번호·키) |
| 시크릿을 주입한다 | 비밀값을 Secret Manager에 저장한다 |
| 함수에 바인딩한다 / 마운트된다 | 함수가 실행될 때 `process.env`로 받을 수 있게 목록에 적는다 |
| 비민감 설정 | 노출돼도 문제없는 값 |
| 평문 노출 | 암호화되지 않은 채 그대로 남음 |
| env config로 제공 | `.env` 파일에 적는다 |
| O-4, E안 | 그 항목이 무엇인지 말로 쓴다 (예: "배포용 비밀값 설정 작업") |

## 문장 쓰기
- 한 문장에 한 가지만 쓴다. 꾸미는 말과 중복 설명은 뺀다.
- 지시만 쓰지 말고 이유를 함께 쓴다 (무엇을 + 왜).
- 이 대화나 이전 작업을 모르는 사람이 처음 읽어도 이해되게 쓴다.

예:
- ❌ "배포되는 `.env`에는 위 두 시크릿을 넣지 않는다(평문 노출 방지)."
- ✅ "토큰·비밀번호(`FB_PRIVATE_KEY`, `DISCORD_BOT_TOKEN`, `REDIS_URL`)는 `.env`에 적지 않는다.
   `.env`는 배포할 때 코드와 함께 올라가서 암호화되지 않은 채 남기 때문이다."

## 예외
- 추적용 ID가 꼭 필요한 기록 문서(PDCA 문서, todo.md)에서는 ID 옆에 뜻을 같이 적는다: `O-4(배포용 비밀값 설정)`
- 코드 식별자(함수·타입 이름)는 바꾸지 않는다. 주석과 문서에서 설명을 덧붙인다.
