# ADR — 배포 아키텍처: 하이브리드 2-프로세스

**Phase**: 1.10 | **상태**: 채택 | **날짜**: 2026-09-28

## 배경

디스코드 봇을 프로덕션에 올리는 데 두 제약이 충돌했다.

1. 공고 수집 스케줄러는 주기 실행(`onSchedule`)만 있으면 되어 serverless(Firebase Functions)가 비용·운영 면에서 적합하다.
2. 그러나 디스코드 인터랙션(슬래시 커맨드·버튼)은 discord.js가 **게이트웨이 WebSocket 연결을 상시 유지**해야 수신된다. serverless는 요청마다 떴다 지므로 WS를 붙들 수 없다.

추가로, 당시 배포 엔트리(`main`)가 인터랙션 게이트웨이를 가리켜 스케줄러 함수가 export되지 않아 **프로덕션에서 자동 수집이 아예 배포되지 않는** 문제(배포 갭)가 있었다.

## 검토한 선택지

- **HTTP 인터랙션 엔드포인트로 전환**: WS를 버리고 인터랙션을 HTTP POST(서명 검증)로 받으면 상시 프로세스가 필요 없어 100% serverless가 된다. 그러나 discord.js 게이트웨이 기반 인터랙션 핸들러(커맨드·버튼·모달·셀렉트)를 전부 다시 짜야 해 범위가 크고 회귀 위험이 높다.
- **단일 상시 프로세스로 통합**: Functions를 버리고 한 프로세스에서 WS + 인프로세스 스케줄러(node-cron). 단순하지만 serverless 이점을 전부 잃는다.
- **문서화만**: `main`을 스케줄러로 돌리고 게이트웨이는 "별도 호스트 필요"로 문서화만. 실제 상시 호스트 구성은 미룸.
- **하이브리드 2-프로세스 (채택)**: 아래.

## 결정

프로세스를 둘로 나눈다.

- **스케줄러**: Firebase Functions `onSchedule`. 공고 동기화 → 변경 감지(diff) → DM까지 한 프로세스 안에서 완결(DM은 REST로 발송하므로 WS 불필요).
- **게이트웨이**: 인터랙션 수신 전용. WS 상시 연결이 필요하므로 무료 상시 호스트(무료 VM + pm2)에 상주. 인바운드 HTTP가 필요 없어 **WS-only**로 둔다.
- 두 프로세스는 **직접 통신하지 않고 Redis·Firestore만 공유**한다.
- 배포 엔트리(`main`)를 스케줄러로 지정해 스케줄 함수가 실제 배포되게 하고, 게이트웨이는 별도 엔트리(`app/gateway.ts`)로 분리한다.

## 근거

- 기존 인터랙션 핸들러를 **그대로 재사용**한다(재작성·회귀 없음) → HTTP 전환안의 가장 큰 비용을 피한다.
- 스케줄러는 serverless 이점(유휴 비용 0)을 유지한다.
- 무료 호스트로 상시 게이트웨이 비용을 0에 가깝게 유지한다.

## 결과 / 트레이드오프

- 게이트웨이는 serverless가 아니다 — 상시 가동 비용은 WS 인터랙션 때문에 불가피하게 지불한다.
- `main` 전환으로 기존 `onRequest`(HTTP) 함수는 Functions에 더는 배포되지 않는다(의도됨).
- 실배포·시크릿 주입(Secret Manager)·Redis 재연결 등 운영 항목은 **Phase 1.14(프로덕션 배포·운영)**로 이월.
- 상시 프로세스 모니터링(생존/이상 감지)은 **Phase 2.1/2.2**에서 다룬다.
