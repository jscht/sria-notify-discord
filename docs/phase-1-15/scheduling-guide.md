## 1. 먼저 알아 둘 것

### 용어

| 용어 | 뜻 |
|------|----|
| 사이트 | 공고를 가져오는 곳입니다. 지금은 sria와 elias 두 곳이며, 둘 다 테스트용 데이터를 돌려줍니다. elias는 지금 코드에서 `temp`라는 이름이고, 이번 작업에서 이름을 바꿉니다 |
| 구독자 | 알림을 신청한 Discord 사용자입니다. 받을 지역과 사이트를 구독 설정에 저장해 둡니다 |
| DM | Discord 개인 메시지입니다. 알림은 DM으로 보냅니다 |
| 스케줄러 | 정해진 시각마다 저절로 실행되는 함수입니다(2절) |
| 갱신 | 사이트에서 공고를 가져와 저장된 공고와 비교하고 바뀐 것을 저장하는 일입니다 |
| Redis | 스케줄러들이 같이 쓰는 빠른 저장소입니다. 무엇을 저장하는지는 2절 "Redis에 저장되는 것"에 있습니다 |
| Firestore | 구독자별 구독 설정(받을 지역과 사이트)을 저장하는 데이터베이스입니다 |
| 락 | 같은 일이 동시에 두 번 실행되지 않게 거는 표시입니다(5절) |

### 어디서 실행되나요

- **Firebase Functions**: 스케줄러가 실행되는 곳입니다. DM도 여기서 Discord API로 직접 보냅니다.
- **Upstash Redis**: 스케줄러가 가져온 공고와 스케줄러끼리 주고받는 값을 저장합니다.
- **Firestore**: 구독 설정을 저장합니다.
- 슬래시 커맨드나 버튼 같은 사용자 조작은 별도 서버(Oracle VM)에서 처리합니다. 이 문서의 범위가 아닙니다. 다만 공고 조회 커맨드가 Redis에 저장된 공고를 읽고, Redis가 비어 있으면 사이트 갱신을 직접 실행합니다(5절).

## 2. 스케줄러

### 스케줄러는 어떻게 실행되나요

- 스케줄러마다 "2시간마다" 같은 일정이 코드에 적혀 있습니다.
- Firebase Functions에 배포하면 이 일정이 Cloud Scheduler(구글의 예약 실행 서비스)에 등록됩니다.
- 일정 시각이 되면 Cloud Scheduler가 그 스케줄러를 실행합니다. 스케줄러는 할 일을 마치면 끝납니다. 다음 일정까지는 아무것도 실행되지 않습니다.

### 이 프로젝트의 스케줄러

스케줄러는 세 개입니다.

| 스케줄러 | 하는 일 | 주기 | DM |
|----------|---------|------|----|
| sria 갱신 | sria에서 공고를 가져와 Redis에 저장 | 2시간 | 보내지 않음 |
| elias 갱신 | elias에서 공고를 가져와 Redis에 저장 | 30분 | 보내지 않음 |
| 알림 | Redis에 저장된 공고에 변경이 있으면 구독자에게 공고 목록을 DM으로 발송 | 매일 06~20시 짝수 정시 (하루 8번) | 보냄 |

sria 갱신과 elias 갱신은 대상 사이트만 다르고 하는 일은 같습니다. 이 문서에서는 둘을 묶어 **사이트 갱신 스케줄러**라고 부릅니다.

### Redis에 저장되는 것

스케줄러들은 Redis에 아래 값을 저장하고 읽습니다. 3절부터 나오는 이름은 모두 이 표의 이름입니다.

| 이름 | 무엇인가 | 누가, 언제 저장하나 | 누가 읽나 |
|------|----------|---------------------|-----------|
| **최신 공고 목록** | 모든 사이트의 최신 공고 | 사이트 갱신이 실행될 때마다 자기 사이트 공고 부분을 고쳐 씀. 사이트 갱신은 사이트 갱신 스케줄러 말고도 알림과 공고 조회 커맨드가 실행할 수 있음 | 알림, 공고 조회 커맨드 |
| **지난 알림 때 목록** | 직전 알림 때의 최신 공고 목록을 그대로 찍어 둔 것. 공고 ID와 내용 비교값만 저장합니다 | 알림이 DM을 다 보낸 뒤 | 다음 알림 |
| **사이트별 마지막 갱신 시각** | 사이트 갱신이 마지막으로 성공한 시각 | 사이트 갱신이 성공할 때 | 알림, 공고 조회 커맨드 |
| **락** | 지금 실행 중이라는 표시(5절) | 각 스케줄러가 시작할 때 걸고 끝날 때 풂 | 각 스케줄러 |

- 최신 공고 목록과 지난 알림 때 목록은 **사용자 구분 없이 모든 공고**를 담습니다.
- 사용자마다 다른 구독 조건은 Firestore에 있습니다. 알림이 DM을 보내기 직전에 이 조건으로 공고를 거릅니다.

```
 sria 갱신  (2시간마다) ──┐
                          ├─ 저장 ─▶ [최신 공고 목록] ──────────┐
 elias 갱신 (30분마다)  ──┘                                 │ 비교 → 바뀐 공고
                                                            ▼
                                              알림 (06~20시)   ─▶ 구독자별로 거르기 ─▶ DM
                                                  │      ▲
                              DM을 다 보낸 뒤 복사 │      │ 비교 기준
                                                  ▼      │
                                             [지난 알림 때 목록]
```

**가져오기와 보내기를 나눈 이유**
- 사이트마다 공고가 바뀌는 속도가 다릅니다. 그래서 가져오는 주기는 사이트마다 따로 둡니다.
- 사용자는 사이트 수와 상관없이 알림 한 번에 DM 한 통만 받습니다. 사이트가 늘어도 DM이 여러 통으로 쪼개지지 않습니다.

창고에 비유하면, 사이트 갱신은 공급처마다 다른 속도로 **창고를 채우는 일**이고, 알림은 정해진 시각마다 쌓인 새 물건을 한 상자에 담아 **배송하는 일**입니다.

**스케줄러끼리는 서로를 모릅니다.**
- "sria 갱신이 끝나면 알림" 같은 실행 순서가 없습니다. 각자 자기 일정대로 실행됩니다.
- 서로 이어지는 것은 위 표의 Redis 값뿐입니다.
- 그래서 실행 시각이 겹칠 수 있습니다. 겹칠 때 어떻게 처리하는지는 5절에 있습니다.

### 실행 시각은 일정 표현이 정합니다

| 일정 표현 | 실행 시각 |
|-----------|-----------|
| `every 2 hours` | 앞 실행이 **끝난** 시각부터 2시간 뒤입니다. 첫 실행은 배포 시각에서 2시간 뒤입니다. 그래서 정각에 맞지 않고 조금씩 밀립니다 |
| `0 6-20/2 * * *` | cron 표현입니다. 매일 06:00부터 20:00까지 2시간마다 정시에 실행됩니다 |

- 사이트 갱신은 `every …` 표현을 그대로 씁니다. 실행 시각이 정각이 아니어도 되기 때문입니다.
- 알림은 사용자가 시각을 예상할 수 있도록 `0 6-20/2 * * *`로 정합니다. 22시부터 04시까지는 보내지 않습니다.
- 시간대를 정하지 않으면 UTC 기준입니다. 그래서 시간대를 `Asia/Seoul`로 지정합니다.

## 3. 사이트 갱신 스케줄러

| 사이트 | 주기 |
|--------|------|
| sria | 2시간 (지금 코드는 4시간, 이번 작업에서 바꿈) |
| elias | 30분 |

한 번 실행될 때 하는 일은 다음과 같습니다.

1. 사이트 갱신 락을 겁니다(5절). 같은 사이트의 갱신이 이미 실행 중이라 락이 걸려 있으면 이번 갱신은 건너뜁니다. 두 갱신이 동시에 저장하면 서로 덮어쓰기 때문입니다.
2. 사이트에서 공고를 가져옵니다.
3. 최신 공고 목록에서 **이 사이트 공고만** 골라 새로 가져온 공고와 비교합니다.
   - 새로 생긴 공고는 추가합니다.
   - 내용이 바뀐 공고는 새 내용으로 덮어씁니다.
   - 새로 가져온 공고에 없는 공고는 지웁니다.
4. 사이트별 마지막 갱신 시각을 지금으로 저장합니다. 알림이 "이 사이트를 방금 갱신했나"를 판단할 때 씁니다.
5. 바뀐 공고가 있으면 `RECRUIT_CHANGED` 이벤트를 발행합니다. 이 이벤트는 기록용이며, **바뀐 공고가 있어도 DM은 보내지 않습니다.** DM은 알림 스케줄러만 보냅니다(4절). 지금 코드는 이 이벤트로 DM을 바로 보내는데, 이번 작업에서 그 연결을 끊습니다.
6. 락을 풀고 끝납니다.

공고 ID가 `sria:…`, `elias:…`처럼 사이트 이름으로 시작하므로, 최신 공고 목록에서 어느 사이트 공고인지 구분할 수 있습니다.

### 실패하거나 0건이면

**사이트에서 공고를 못 가져오면** 오류로 처리하고 최신 공고 목록을 건드리지 않습니다. 그 사이트 공고는 이전 상태로 남습니다.

**정상 응답이 0건이면** 그 사이트 공고를 모두 지우고 경고 로그를 남깁니다. 다만 사이트 코드 오류로 0건이 나와도 진짜 0건과 구분할 수 없어 지워집니다. 경고 로그로 원인을 찾습니다. 지금은 두 사이트 모두 mock 데이터이고, 실제 사이트를 연결할 때는 공고를 읽지 못하면 오류를 내도록 만듭니다.

### 공고가 Redis에서 사라지는 경우

**공고 하나가 사라지는 경우**는 사이트 갱신이 정합니다. 사이트에서 빠진 공고를 다음 갱신 때 지웁니다(위 3단계). 공고마다 타이머가 따로 있지는 않습니다.
- elias: 모집 기간 12시간이 지나거나, 갱신마다 5% 확률로 빠집니다(테스트용 데이터 규칙).
- sria: 데이터 파일에서 공고를 지우면 빠집니다.

**최신 공고 목록 전체가 사라지는 경우**는 Redis 만료 시간 때문입니다.
- 최신 공고 목록은 Redis 키 하나에 모두 들어 있고, 이 키에 6시간 만료가 걸려 있습니다.
- 어느 사이트든 갱신할 때마다 만료 시간이 6시간으로 다시 맞춰집니다. 그래서 **모든 사이트의 갱신이 6시간 넘게 멈춰야** 최신 공고 목록이 사라집니다. 정상 운영에서는 일어나지 않습니다.
- sria 갱신만 멈추고 elias 갱신이 계속 실행되면, sria 공고는 사라지지 않고 마지막 상태로 남습니다.
- 이 동작은 원래 있던 것이고(2025-01-11, 커밋 `8402689`), 이번 작업에서 바꾸지 않습니다.

## 4. 알림 스케줄러

매일 06시부터 20시까지 짝수 정시에 다음 순서로 실행됩니다. 22시부터 04시까지는 보내지 않고, 그사이 바뀐 공고는 06시 알림이 한 번에 보냅니다. 사이트 갱신은 밤에도 계속합니다.

1. 알림 락을 겁니다. 이미 걸려 있으면 다른 알림이 실행 중이므로 바로 끝냅니다. 알림이 두 번 실행되면 DM이 두 번 나가기 때문입니다.
2. 사이트마다 동시에 갱신을 한 번 더 실행해 최신 공고 목록에 지금 갱신된 공고를 반영합니다. sria는 마지막 갱신이 최대 2시간 전일 수 있기 때문입니다. 방금 갱신한 사이트는 건너뜁니다(5절). 갱신에 실패한 사이트가 있고 최신 공고 목록이 비어 있으면 아무것도 저장하지 않고 끝냅니다. 비교 기준과 Firestore 목록을 지키기 위해서입니다.
3. 최신 공고 목록을 지난 알림 때 목록과 비교합니다. 지난 알림 때 목록에 없거나 내용이 달라진 공고가 **이번 회차의 바뀐 공고**입니다. 새로 생긴 공고, 내용이 바뀐 공고, 마감으로 바뀐 공고가 여기에 들어갑니다. 이 단계는 모든 사용자에게 공통이라 한 번만 합니다.
4. 최신 공고 목록에서 사용자에게 보이지 않게 설정한 사이트의 공고를 빼고 정렬합니다. 접수중 → 발표중 → 종료 순서로 놓고, 같은 상태 안에서는 최신순입니다. 마감된 공고도 빼지 않고 뒤에 둡니다.
5. Firestore에서 구독자 목록을 읽습니다. 구독자마다 구독한 사이트와 지역에 맞는 공고를 고릅니다. 그중 바뀐 공고가 하나라도 있으면, 바뀌지 않은 공고까지 포함한 목록 전체를 DM 한 통으로 보냅니다. 바뀐 공고가 없으면 그 구독자에게는 보내지 않습니다. 한 사람에게 보내다 오류가 나도 다음 사람에게는 계속 보냅니다.
6. 최신 공고 목록을 그대로 지난 알림 때 목록으로 저장합니다. 다음 알림은 이 목록과 비교합니다. 이 목록에는 만료 시간이 없습니다. 어디까지 알렸는지 표시하는 기준이라, 밤이나 장애로 알림이 쉬어도 남아 있어야 하기 때문입니다.
7. 최신 공고 목록을 Firestore에도 저장합니다. Redis 목록이 비어 있고 사이트 갱신까지 실패했을 때, 공고 조회 커맨드가 이 목록을 보여 주기 때문입니다. 저장이 실패해도 알림은 정상으로 끝나고, 다음 알림에서 다시 저장합니다.
8. 알림 락을 풀고 끝납니다.

### 왜 "지난 알림 때 목록"과 비교하나요?

사이트 갱신도 실행될 때마다 바뀐 공고를 찾습니다. 하지만 갱신이 아는 것은 "직전 **갱신**보다 바뀐 것"뿐입니다. 알림에 필요한 것은 "직전 **알림**보다 바뀐 것"입니다.

예를 들어 elias 공고 A가 10:30에 생겼다고 해 보겠습니다.
- 10:30 갱신은 A를 새 공고로 봅니다. 하지만 DM은 보내지 않습니다.
- 11:00 갱신은 A가 이미 저장돼 있으니 "변경 없음"으로 봅니다.
- 12:00 알림이 갱신 결과만 본다면 A를 놓칩니다.
- 지난 알림 때 목록(10:00 저장)에는 A가 없습니다. 그래서 12:00 알림은 A를 바뀐 공고로 찾아냅니다.

### 왜 바뀐 공고만이 아니라 목록 전체를 보내나요?

DM은 "지금 지원할 수 있는 공고 목록"을 다시 알려 주는 역할입니다. 바뀐 공고는 DM을 보낼지 정하는 계기일 뿐입니다. 접수 중 공고가 위에 정렬되므로, 마감 소식이 계기가 되어도 사용자는 쓸모 있는 목록을 받습니다.

### 두 알림 사이에 생겼다가 사라진 공고는요?

보내지 않습니다. 11:00에 생겼다가 11:30에 사라진 공고는 12:00에 비교할 때 이미 최신 공고 목록에 없기 때문입니다. 그 사이 "종료"된 공고는 목록에 남아 있으므로 보내되, 정렬로 목록 아래쪽에 갑니다.

### 실패하거나 겹치면

**배포 직후 첫 알림은 어떻게 되나요?**
지난 알림 때 목록이 없으므로, 최신 공고 목록을 저장만 하고 DM은 보내지 않습니다. 이 키를 직접 지운 경우도 같습니다. 이미 받은 공고를 전부 다시 받는 일을 막으려는 것입니다. 대신 그 회차에 생긴 새 공고는 알리지 않습니다.

**서비스 중에 다시 배포하면요?**
영향이 없습니다. 지난 알림 때 목록은 Redis에 있어서 배포해도 지워지지 않습니다. 다만 비교값은 공고 JSON 전체로 계산하므로, 배포로 공고 필드나 데이터가 바뀌면 그 공고는 바뀐 공고가 되어 DM이 한 번 더 나갈 수 있습니다.

**같은 알림이 두 번 실행되면요?**
Cloud Scheduler가 같은 실행을 두 번 보내는 경우가 있습니다. 뒤 실행은 알림 락에 막혀 바로 끝나므로 DM은 한 번만 나갑니다(5절).

**DM을 보내다가 중간에 멈추면요?**
지난 알림 때 목록을 저장하기 전에 멈췄으므로, 다음 알림이 같은 공고를 다시 보냅니다. 일부 사용자는 같은 DM을 두 번 받을 수 있습니다. 공고를 놓치는 것보다 두 번 받는 쪽을 택했습니다. 알림 락은 5분 뒤 저절로 풀립니다.

**구독자 한 명에게 DM을 못 보내면요?**
DM 발송 함수가 그 자리에서 최대 3번 다시 시도합니다. 그래도 실패하면 로그만 남기고 다음 사람에게 보냅니다. 지난 알림 때 목록은 그대로 저장하고, 실패한 사람을 따로 기억하지 않습니다. 그 사람은 다음에 DM을 받을 때 아직 남아 있는 공고를 함께 받습니다. 실패는 드물고, 다음 DM에서 공고를 다시 볼 수 있어서 이렇게 정했습니다.

**구독자 목록을 못 읽으면요?**
알림이 오류로 끝나고 지난 알림 때 목록도 저장하지 않습니다. 다음 알림에서 다시 시도합니다.

## 5. 사이트 갱신 스케줄러와 알림 스케줄러의 관계

### 서로 어떤 관계인가요

- 사이트 갱신 스케줄러는 최신 공고 목록을 저장하고, 알림 스케줄러는 그 목록을 읽어 지난 알림 때 목록과 비교합니다.
- 사이트 갱신 스케줄러는 알림을 실행하지 않습니다. DM은 알림 스케줄러만 보냅니다.
- 알림 스케줄러는 시작할 때 사이트 갱신을 직접 실행합니다(4절 2단계). 그래서 알림 스케줄러와 sria 갱신(또는 elias 갱신) 스케줄러가 같은 사이트를 동시에 갱신하려는 일이 생길 수 있습니다. 그때의 처리는 아래 항목에서 설명합니다.

### 함께 돌아가는 방식

아래는 세 스케줄러가 정각에 맞춰 실행된다고 가정한 예입니다. 실제 실행 시각은 일정 표현에 따라 다릅니다(2절).

| 시각 | elias 갱신 스케줄러 | sria 갱신 스케줄러 | 알림 스케줄러 |
|------|-----------|-----------|------|
| 10:00 | 갱신 | 갱신 | 두 사이트 모두 방금 갱신했으므로 건너뜀 → 비교·발송 |
| 10:30 | 갱신 | | |
| 11:00 | 갱신 | | |
| 11:30 | 갱신 | | |
| 12:00 | 갱신 시작 | 갱신 시작 | 두 사이트 갱신을 기다렸다가 그 결과를 씀 → 비교·발송 |

12:00 알림은 10:30부터 12:00까지 elias 갱신 네 번에서 쌓인 변경을 한 번에 보냅니다.

### 락: "사용 중" 팻말

같은 일이 동시에 두 번 실행되지 않게 하려고 **락**을 씁니다. 락은 회의실 문에 거는 "사용 중" 팻말과 같습니다.
- 들어가기 전에 팻말을 봅니다. 걸려 있으면 들어가지 않습니다.
- 비어 있으면 팻말을 걸고 들어가고, 나올 때 뗍니다.
- 팻말에는 타이머가 있습니다. 안에 있던 작업이 멈춰서 팻말을 못 떼도 시간이 지나면 저절로 떨어집니다. 그래서 다음 작업이 영원히 막히지 않습니다.

락은 두 종류입니다.
- **사이트 갱신 락**(타이머 60초): 사이트마다 따로 겁니다. 같은 사이트의 갱신이 동시에 저장하는 것을 막습니다. sria와 elias는 서로 다른 공고만 다루므로 동시에 갱신해도 됩니다.
- **알림 락**(타이머 5분): 알림이 두 번 실행되어 DM이 두 번 나가는 것을 막습니다.

### 알림이 사이트를 다시 갱신할 때의 규칙

- **5분 안에 갱신한 사이트는 건너뜁니다.** 방금 가져온 공고를 다시 가져올 필요가 없기 때문입니다.
- **그 사이트를 갱신하는 중이면 기다립니다.** 1초마다 다시 확인합니다.
  - 기다리던 갱신이 성공해 끝나면, 다시 갱신하지 않고 그 결과를 씁니다.
  - 기다리던 갱신이 실패하면, 알림이 직접 갱신합니다.
  - 60초가 지나도 끝나지 않으면 실패로 처리합니다. 최신 공고 목록에 공고가 있으면 그 목록으로 진행하고, 비어 있으면 아무것도 저장하지 않고 끝냅니다.

기다리는 이유는 저장 중인 최신 공고 목록을 읽지 않기 위해서입니다. 시뮬레이션(2026-10-14)에서 기다리지 않고 바로 넘어가면 24.8%가 저장 중인 목록을 읽었습니다. 기다리면 0%였고, 기다린 시간은 평균 3.5초, 최대 10초였습니다.

반대로 알림이 elias를 갱신하는 중에 elias 갱신 스케줄러의 차례가 오면, elias 갱신 스케줄러는 락이 걸려 있으므로 이번 실행을 건너뜁니다. 30분 뒤 다음 차례에 다시 실행됩니다.

### 공고 조회 커맨드가 사이트를 갱신할 때

공고 조회 커맨드는 Redis 최신 공고 목록이 비어 있으면, 알림과 같은 규칙으로 사이트마다 갱신을 실행합니다. 5분 안에 갱신한 사이트는 건너뛰고, 갱신 중이면 기다립니다. 배포 직후 첫 예약 실행 전(elias 최대 30분, sria 최대 2시간)에 조회해도 빈 결과가 나오지 않는 것은 이 때문입니다.

갱신까지 실패하면 Firestore 목록을 보여 주기만 하고 Redis에는 쓰지 않습니다. 오래된 목록이 최신 공고 목록에 섞이지 않게 하기 위해서입니다.

### Redis 키

| 키 | 담는 것 | 쓰는 쪽 | 읽는 쪽 | 만료 |
|----|---------|---------|---------|------|
| `recruit:city:all` | 최신 공고 목록 (공고 ID → 공고 내용) | 사이트 갱신 (알림·공고 조회 커맨드가 실행한 갱신 포함) | 알림, 공고 조회 커맨드 | 6시간, 갱신마다 다시 맞춤 |
| `recruit:hash:city:all` | 직전 갱신 때 공고별 비교값 | 사이트 갱신 | 사이트 갱신 | 6시간, 갱신마다 다시 맞춤 |
| `recruit:notified:all` | 지난 알림 때 목록 (공고 ID → 비교값). 목록이 비면 표시 항목 `__empty__` 하나만 있음 | 알림 | 알림 | 없음 |
| `recruit:lastSync:{source}` | 사이트별 마지막 갱신 성공 시각 | 사이트 갱신 | 알림, 공고 조회 커맨드 | 1일 |
| `lock:recruit:sync:{source}` | 사이트 갱신 락 | 사이트 갱신 | 사이트 갱신 | 60초 |
| `lock:notification` | 알림 락 | 알림 | 알림 | 5분 |

- 비교값은 공고 내용을 sha256으로 계산한 값입니다. 내용이 한 글자라도 바뀌면 값이 달라집니다.
- `recruit:hash:city:all`과 `recruit:notified:all`은 모양이 같지만 기준 시점이 다릅니다. 앞의 것은 직전 **갱신**, 뒤의 것은 직전 **알림** 때의 상태입니다.
- 최신 공고 목록과 비교값에 쓰는 함수는 사이트 갱신(`syncRecruits`) 하나입니다. 그래서 누가 실행하든 사이트 갱신 락과 사이트 구분을 똑같이 따릅니다.

### 사이트 갱신 스케줄러와 알림 스케줄러 비교

| | 사이트 갱신 스케줄러 | 알림 스케줄러 |
|---|---|---|
| 못 시작하는 경우 | 사이트 갱신 락이 걸려 있으면 건너뜀 | 알림 락이 걸려 있으면 끝냄 |
| 읽는 것 | 사이트 데이터, 직전 갱신 비교값 | 사이트별 마지막 갱신 시각, 최신 공고 목록, 지난 알림 때 목록, Firestore 구독자 목록 |
| 쓰는 것 | 최신 공고 목록, 비교값, 마지막 갱신 시각, Firestore 마지막 갱신 시각 | 다시 갱신할 때 사이트 갱신과 같은 것, 지난 알림 때 목록, Firestore 공고 목록 |
